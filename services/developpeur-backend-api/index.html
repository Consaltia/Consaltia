Les API que je conçois

  • Intégration entre deux systèmes qui ne se parlaient pas

  • Traitements planifiés et webhooks

Ce qui distingue une API tenable dans le temps

La différence entre une API qui tient et une API qu'on finit par contourner ne se voit pas à la livraison. Elle se voit au premier changement de besoin.

  • Un contrat documenté, tenu, et versionné quand il doit changer
  • Des erreurs explicites, qui disent quoi corriger et non seulement que ça a échoué
  • Pagination et filtrage prévus dès le départ, pas ajoutés sous la pression
  • Opérations rejouables sans effet de bord, ce qui sauve les reprises après incident
  • Traces et métriques, pour diagnostiquer sans deviner
  • Tests sur les règles métier, là où une régression coûte le plus

Questions fréquentes

REST ou GraphQL ?

REST dans la majorité des cas : plus simple à mettre en cache, à documenter et à reprendre. GraphQL quand plusieurs clients très différents consomment les mêmes données et que la sur-récupération devient un vrai coût.

Node.js ou Spring Boot ?

Node.js quand le front est déjà en JavaScript et que l'équipe est unifiée sur un langage. Spring Boot quand l'écosystème est en Java, que les règles métier sont lourdes ou que l'environnement est très encadré. J'ai livré les deux.

Livrez-vous la documentation ?

Oui, elle fait partie du travail et non d'une option. Une API sans contrat lisible oblige le client suivant à lire le code source.
